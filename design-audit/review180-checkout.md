**Seat:** Checkout UX Engineer · **Wave:** 180 (redesign waves 181–188 landed in code; wave labels in source run ahead of this review number)
**Scope (review only, no source edits):** `frontend/src/pages/checkout/[id].astro`, `frontend/src/pages/pay/[slug].astro`
**Supporting files read:** `frontend/src/lib/ui.ts`, `frontend/src/lib/api.ts`, `frontend/src/lib/i18n.ts`, `frontend/src/layouts/BaseLayout.astro`, `frontend/src/styles/tokens.css`, `crates/api/src/handlers/payments.rs` (`checkout_details`), `crates/api/src/handlers/payment_links.rs` (`PublicLinkView`, `pay_link`)
**Baseline:** Wave 151 audit `design-audit/06-checkout-ux.md` (the task brief named it `06-checkout.md`; the file on disk is `06-checkout-ux.md`) — findings C-01…C-12.
**Test lens (unchanged):** 360×640 Android, one thumb, intermittent 3G/4G, payer leaves for the bKash/Nagad app and returns.

## Verdict in one paragraph

This is a real redesign, not a reskin: steps, gateway radio cards (pay page only), field-level validation, polling, copy fields, a proper trust row and a brand-contrast gate all landed, and they close or half-close seven of the twelve Wave 151 findings. But the two conversion-killers from Wave 151 are still standing, for different reasons. **C-03 is only half-fixed:** `/pay` got radio cards, `/checkout` still renders the gateway as a read-only text row and silently submits `gateways[0]`. **C-02 is unfixed:** the pay-link flow still terminates at "Payment started" with no sender-number/TrxID capture, so if SMS matching fails there is still no in-page recovery. And **C-01 — the recipient number — cannot be fixed in the frontend at all** (see §3): the design's honest handling of that constraint is the single most important judgment in this review.

## 2. What still hurts conversion / trust

### 2.1 Checkout still has no gateway choice (C-03, half-open)
`/pay` got radio cards; `/checkout` did not. The gateway is still a read-only summary row (`checkout:97-100`), still comma-joined when several exist (`gatewayDisplay()`, `checkout:494-499`), and submission still silently pins the first one (`currentGateway = … details.gateways?.[0] …`, `checkout:706-708`, submitted at `817`). A Nagad-only payer handed a bKash-first checkout still has exactly one option: abandon. This is now the largest *pure-frontend-fixable* conversion leak, because the payload type already carries `gateways?: string[]` (`lib/api.ts` `CheckoutDetails`) — although see §3: the live `checkout_details` handler currently returns a single `gateway`, so cards would today render a choice of one.

### 2.2 The pay-link flow still ends before the payment does (C-02, open)
Submit still replaces the form with the "Payment started" card (`pay:124-151`, transition at `pay:580-586`) containing Transaction ID, Reference and Amount — and then nothing. No sender-number field, no TrxID field, no status polling, no link onward to a checkout. If the merchant's SMS never matches, the payer's only recourse is out-of-band contact with a reference string in hand. The reference still falls back to the slug (`pay:571`: `result.reference ?? slug`) — verified server-side this is not a UI invention: `pay_link` stores `reference: Some(slug)` and `PayLinkResponse` returns only `transaction_id` + `status`, so the "reference" the payer is told to "use exactly as shown" (`pay:140-144`) *is* the public slug. The design presents a meaningless string with maximum ceremony (mono copy field) and never says where in the bKash/Nagad flow it should be entered.

### 2.3 Polling starts one step too late (new defect in the C-05 fix)
Polling only starts inside `render()` when a *loaded* status is `processing` (`checkout:642`). The primary path — payer submits the form on this page — never enters it: the submit handler hides the form and shows the static `submitted-area` (`checkout:819-825`) without calling `startPolling()` or `refreshStatus()`. So the payer who most needs live confirmation must reload the page to get it, and the submitted/processing duplication the audit flagged (§1.1 step 8) survives: two near-identical messages, and the one the payer actually sees is the one with no spinner, no Check-status button and no polling. Polling also stops silently after ~3 min with no escalation copy, no recap of amount/TrxID, and no "paid but not matched?" fallback; it does not pause when the tab is hidden, so a backgrounded tab burns the full 30 ticks and then gives up before the payer returns from the wallet app.

### 2.4 Steps exist but don't track the pay page's real journey
On `/pay`, `setSteps()` is called exactly once — on success, jumping 1 → 3 (`pay:580`). During the entire form the indicator sits on step 1 "Review" while the payer is in fact paying, and step 2 "Pay" is never the current step on that page. On checkout the mapping is better (pending → 2, processing → 3, completed → 4 at `checkout:640`) but step 3 is labelled "Confirmed" while it is used for the *processing/unconfirmed* state — the indicator asserts the one thing the page copy correctly refuses to assert.

### 2.5 Remaining friction (each small, together they are the drop-off)
- **Amount still not sticky, still not the hero on checkout (C-08, open).** `.sticky-summary` exists in the shared CSS (`BaseLayout.astro:213`) and is used by *neither* page. Checkout amount is still 1.375 rem (`checkout:298-301`) — the same size as the merchant `<h1>` — in a summary row that scrolls away, and the submit button still reads "I have paid — submit details" (`checkout:172-174`) with no amount or gateway. The audit's §4.3 spec was built and then not adopted.
- **Instructions are still a paragraph, and a fictional one (C-01 adjacent).** Default text (`checkout:127-131`) still says "send the amount shown above to the merchant using the payment method above" — no numbered steps, no Send-Money-not-Cash-Out, no "come back here" warning. Merchant `instructions` would override it (`checkout:740-741`), but the live API never returns that field (§3), so in production the generic paragraph is the only instruction every payer will ever see.
- **No state survives the wallet-app round trip.** Neither page persists in-progress input (`sessionStorage`/`localStorage` grep: none in either file). Android discarding the tab while the payer is in bKash still loses a typed TrxID — the exact failure the audit §1.3 flagged.
- **No Retry anywhere.** Load errors are still terminal cards (`checkout:53-60`, `pay:35-43`); checkout still surfaces raw API text to the payer (`checkout:771-775`). Three different failures (expired / not found / network) still share one recovery: reload and hope.
- **Completed is still not a receipt.** No amount, gateway, TrxID, timestamp, share/save affordance or return-to-merchant CTA (`checkout:202-206`) — no proof artefact for the Messenger dispute, which is how these are actually settled.
- **Redirect and manual paths still compete.** The redirect button renders *in addition to* the pending manual form with no either/or framing (`checkout:114-121` + `123-176`).
- **FX selector still sits mid-summary on both pages** (`checkout:107-111`, `pay:53-57`), still auth-gated so it normally never appears for anonymous payers — dead weight that, if it ever appears, invites "which amount do I send?" errors.
- **Validation edges.** The BD regex is immediately undercut by a fallback accepting *any* 6–15 digit string (`checkout:797`, same pattern `pay:546`), so `123456` passes as a wallet number; TrxID is one generic 6–20 rule for all gateways, not bKash's 10-character format, and there is no auto-uppercase/mono styling on the field. Checkout's two field-error strings are hard-coded English (`checkout:798,803`) while pay's correctly go through `t()` (`pay:547,555`). On `/pay`, amount errors still use the top banner (`pay:539-542`) instead of the field pattern used two fields later, and the gateway-required check (`pay:560-564`) is dead code — a radio is always pre-checked.
- **i18n is still partial (C-10, open).** Hard-coded English on payer surfaces: both trust rows, checkout hints/instructions/submit label/redirect copy, pay gateway names + "Send money"/"Bank or cash" hints (`pay:102-107`), copy-button labels. Amounts still render `en-US` numerals via `formatMoney()` in all modes.
- **Pre-selected bKash manufactures consent (C-04's UX half).** The pay-page cards are still a hard-coded list of six (`pay:102-107`) with `bkash` `checked` by default — not the merchant's enabled gateways. `PublicLinkView` returns no gateway list (§3), so the frontend cannot do better today; but defaulting the selection *and* ordering by platform preference rather than the payer's last-used gateway are frontend choices.
- **Expiry is decoration.** Checkout renders `expires_at` if present (`checkout:716-722`) as a locale datetime, never a countdown — and the live handler doesn't return it at all (§3), so the row never appears.

## 3. The recipient-number constraint — stated honestly

**The public API does not expose the merchant's receiving wallet number. This is verified, not assumed:**

- `GET /api/v1/checkout/:id` (`checkout_details`, `crates/api/src/handlers/payments.rs`) returns exactly: `transaction_id`, `amount`/`amount_display`/`amount_minor`, `currency`, a single `gateway`, `status`, merchant/business name, and branding (`display_name`, `brand_name`, `brand_color`, `logo_url`, `checkout_message`). No recipient number, no `gateways[]`, no `instructions`, no `expires_at`, no `description`, no `redirect_url` — every one of those fields in the frontend's defensive `CheckoutView` (`checkout:395-425`) is dead code against the current backend.
- `GET /api/v1/payment-links/public/:slug` (`PublicLinkView`, `crates/api/src/handlers/payment_links.rs`) returns `title`, `description`, `amount`, `merchant_name`, `collect_phone`, `collect_email`, `branding`. No recipient number, no gateway list.

**Judgment within that constraint:** C-01 is therefore *not* a frontend failure and this review does not rank it as one. A payer still cannot complete a manual payment from these screens alone — that fact hasn't changed since Wave 151 — but the fix belongs to the API contract (per-gateway recipient instructions in both public payloads, audit §4.5 item 1), not to these two files.

**What the design does about it — and what it doesn't:**

- ✅ It does not fake it. No placeholder number, no invented "merchant wallet" field, nothing that could send money to a wrong or fabricated destination. On a payment page, that restraint is the right call and worth saying plainly.
- ✅ Copy infrastructure is built and waiting: `.copy-field` + `copyText()` are live for reference/transaction IDs today, so the day the API ships a recipient number it drops into an existing, tested pattern instead of needing new UI.
- ✅ The trust row and instructions correctly avoid promising a number ("using the payment method above" is vague, but it is not false).
- ❌ It does not *acknowledge* the gap to the payer. Nothing on either page says "the merchant will give you / has given you the number to send to" or names the out-of-band channel to expect it on. The payer is left to discover the missing step inside the wallet app — the worst possible moment. One honest line in the instructions block ("Send to the {gateway} number the merchant gave you — it isn't shown here") costs nothing, needs no API change, and converts a dead end into an expected step.
- ❌ It does not use the one channel it has: merchant free-text. `checkout_message`/branding renders on both pages, but no merchant-facing guidance (outside this review's scope) tells merchants "put your receiving number in your checkout message — the page cannot show it automatically." Until the API lands, that message field *is* the recipient-number surface, and the design treats it as decoration.
